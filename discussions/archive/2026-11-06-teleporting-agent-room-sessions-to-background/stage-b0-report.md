**How it works.** A node is a temporary folder with its own bare Git storage (`store.git`),
separate from the project's repository. Its parts:
- **Capture.** Each round becomes one commit on `refs/lines/<discussion>/<node>`. It's built from
  the folder's bytes with `hash-object --no-filters`, a temporary index and `commit-tree`.
  Symlinks are refused.
- **Transfer.** The sender POSTs an **offer** (protocol, room, discussion, node, commit, base).
  The receiver answers "have" (it already published that commit) or "send". The sender then
  POSTs a **bundle**: incremental from the last acknowledged commit, or full. If the receiver
  answers `missing-base`, the sender retries once with a full bundle.
- **Receiving.**
  - The upload is saved to `tmp/`. Then the receiver checks the bundle header (exactly one head,
    named for the expected identity, equal to the offered commit; prerequisites present) and
    runs `bundle verify`.
  - It imports with `fetch` (with `fetch.fsckObjects`) into a temporary `refs/incoming/…` ref,
    then checks the tree (file types, paths, limits, name collisions) and the ancestry, then the
    metadata schema and identity.
  - It writes the snapshot into `snapshots/.staging-…` with `cat-file`, never a Git checkout, so
    no filters or attributes run. It then renames the folder to `snapshots/<commit>` and makes it
    read-only.
  - **Publishing** is one atomic rename of `published.json`. Then `refs/received/…` follows, and
    the receiver acknowledges the exact commit.
- **Restart recovery** runs when a node opens. It removes uploads, staging folders, never-published
  snapshots and incoming refs, and points the received ref back at `published.json`.

All Git runs use argument arrays (`execFile`), never a shell, with
`-c core.hooksPath=/dev/null`, no system or global Git config, and no automatic gc.
Fixed identities: room `room-b0`, discussion `disc-1`, nodes `node-1` (sender) and `node-2`
(receiver, paired with `node-1` only). Commit dates are fixed, so the same fixtures always give
the same commit IDs.

**Restart points.** Each receive ran in a **separate process**, which exited abruptly (exit code
86, no cleanup). Then the node was reopened, which counts as a restart:

| Interruption point | Left on disk at the crash | After restart |
|---|---|---|
| after the upload was saved | 1 upload | old snapshot published, upload removed; resend → `incremental`, acknowledged |
| after import | 1 upload, 1 incoming ref | old snapshot; leftovers removed; resend acknowledged |
| **during materialization** (half the files written) | 1 upload, 1 staging folder, 1 incoming ref | old snapshot, staging folder removed; resend acknowledged |
| after materialization, before publishing | 1 upload, 1 complete but unpublished snapshot, 1 incoming ref | old snapshot, the unpublished one removed; resend acknowledged |
| **after publishing, before the acknowledgement** | 1 upload, 1 incoming ref; pointer and received ref on the new round | new snapshot (complete, = commit); resend → `already-had`, same commit acknowledged |

In every case, after the restart the pointer named a complete snapshot that matched its commit
file by file. Nothing from staging was visible, and the old snapshot's digest was unchanged.

**Not tested** (interruption points):
- a crash between the `published.json` rename and the received-ref update. Recovery has code for
  it (`refRepaired`), but no run exercised it;
- a crash while `published.json.tmp-…` is being written;
- a crash inside `git fetch` itself (Git's own partial pack files are not cleaned up);
- crashes on the **sending** side (between capture and recording the ack);
- power loss: there's no folder `fsync`, so durability after a power cut is unproven.

## 5. Recommendation: the file boundary for stage B (yours to decide, Q1)

**Recommended: a new `src/replicate.mjs`.** Reasons:
- The protocol alone is already ~340 lines here. Stage B adds pairing, per-peer queues with
  bounded retry and backoff, round-end capture with its writer gate, and snapshot reads. So it
  will probably end up around 500–700 lines (an estimate). `ui.mjs` (944 lines) and `docs.mjs`
  (995 lines) are already the two biggest files. Adding this to either would roughly double it
  and mix two jobs.
- It has its own clear interface. Almost nothing in it touches the UI, and the prototype's parts
  map onto it directly: capture, send, the receive handler, recovery, and "which snapshot to
  show".
- It is easy to remove or disable (no `--peer` → never loaded), and easy to test on its own,
  like here.

What would stay in existing files: a call at round end and recovery at startup in `ui.mjs`,
`--node`/`--peer` in `cli.mjs`, and in `docs.mjs` routing `POST /replica/*` to the new module's
handler plus snapshot-aware reads. The alternative (no new file) would put the protocol into
`ui.mjs`. It works, but it makes the largest file harder to read in one sitting.

## 6. What wasn't checked
- **The Pi (charon), a real LAN, two separate machines or processes over a network.** Both nodes
  ran on one Mac over 127.0.0.1. Only the restart checks used a second process.
- **Real rounds.** The rounds were scripted file edits, with no model calls. The round metadata is
  minimal: no conversation entries, agent order or models yet.
- Pairing, scheduling, bounded retry/backoff, timers, per-peer queues and coalescing are
  **deferred to stage B**. The send here is one call, made by hand.
- Two senders, or a node that both sends and receives, at the same time.
- The interruption points listed under "Not tested" in section 2; power loss; disk full.
- Large folders or files (limits exist but only the bundle-size limit was exercised); Unicode
  normalization collisions (code exists, no check ran); Windows.
- Old-snapshot clean-up and disk growth over many rounds.
- The browser and UI: not involved in B0.

**B0 doesn't establish production readiness.**
